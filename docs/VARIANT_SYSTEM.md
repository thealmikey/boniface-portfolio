# Variant System Specification

**Version:** 2.0 — Variant Laboratory  
**Date:** 2026-08-11  
**Status:** Active specification

---

# What a Variant Is

A variant is a **complete hypothesis** about how Beverly should be positioned to a particular audience.

Beverly has one career with many possible framings. A variant reframes that career for a specific audience, opportunity type, or market context. The underlying facts remain constant; the lens through which they are presented changes.

## Variant ≠ Theme

A theme changes colors and fonts. A variant changes:
- What Beverly is *known for*
- What problems she solves
- What outcomes she emphasizes
- Who she is speaking to
- What visual metaphors reinforce her positioning
- How the page is structured and read

The variant system is a **positioning engine**, not a skin switcher.

---

# The Variant Laboratory

## Concept

The Variant Laboratory treats each variant as an independent design experiment. Every variant may:

- Reorder sections entirely
- Change typography voice and density
- Reshape the hero composition
- Rethink the metrics presentation
- Redesign service cards, timelines, or grids
- Alter whitespace and visual hierarchy
- Change the CTA strategy

All while preserving canonical facts.

## Design Theses

Each variant is driven by an explicit **Design Thesis** — a statement about the audience, the hypothesis, and the visual strategy. No two variants should look or read the same.

## 02 — Strategist: The Strategic Operator

### Audience

### Professional Hypothesis
Beverly's most valuable positioning is as a strategic operator who can enter any complex organization and bring order to chaos. The audience needs to see authority, restraint, and operational gravitas — not marketing flair.

### Core Message

### Primary CTA
"Let's talk about what you're trying to improve"

### Content Emphasis
- Hero: Name only, ultra-minimal. No subtitle, no statement. Let the name carry weight.
- Summary: Condensed to 2-3 powerful points. No bullet decoration.
- Metrics: Reduced to 2-3 most executive-relevant metrics (reporting accuracy, years of experience). Others de-emphasized or removed.
- Experience: Featured roles only (SAP, LinkedIn). Earlier roles summarized or removed from primary view.
- Services: Condensed to 3-4 strategic capabilities. No expandable details — too transactional.
- Engagement: Single "Ongoing Partnership" emphasized. Others minimized.

### Section Order
1. Hero (name only)
2. Summary (minimal)
3. Featured Metrics (2-3 only)
4. Selected Experience (SAP + LinkedIn)
5. Strategic Capabilities (condensed)
6. Engagement (single model)
7. Contact

### Visual Language
Ultra-minimalist. Black, ivory, and a single accent line. No gradients, no patterns, no decoration. Authority through emptiness. Think: high-end consulting firm or law practice.

### Typography
- Display: Playfair Display (serif authority, lighter weight)
- Body: Inter (clean, understated)
- Hero: Massive serif, light weight, maximum tracking
- Body: Tight leading, restrained color palette

### Layout Model
Asymmetric. Hero name pushed to left, not centered. Metrics as a single horizontal band, not stacked. Experience as a tight list, not expanded cards. Generous negative space signals confidence.

### Metrics Emphasis
Extreme reduction. Only 2-3 metrics shown. Large type. High contrast. No decorative context. The numbers speak for themselves.

### Experience Emphasis
Curated, not chronological. SAP and LinkedIn featured prominently. Earlier roles exist as a compact reference, not a timeline. Emphasis on decision-making scope, not task lists.

### Services Emphasis
Strategic framing only. No "includes" lists. No "best for" copy. Services stated as capabilities, not packages. High-level, not transactional.

### What Makes It Different
Removes everything that isn't essential to the strategic positioning. It is the anti-marketing variant — it trusts the audience to understand value without being sold to. The whitespace is the message.

## CSS Architecture

### Base Layer (Shared)

```css
/* All variants inherit these structural foundations */
.hero { /* base hero */ }
.metrics-band { /* base metrics */ }
.experience-grid { /* base experience */ }
.services-list { /* base services */ }
.outcome { /* base outcome */ }
```

### Variant Override Layer

Each variant overrides structural properties via attribute selectors:

```css
[data-variant="strategist"] .hero {
  text-align: left;
  padding: var(--pad-y) 0;
}

[data-variant="revenue"] .metrics-band {
  background: #0a0a0a;
  padding: calc(var(--pad-y) * 1.5) var(--pad-x);
}

[data-variant="bridge"] .hero {
  text-align: left;
  background: linear-gradient(...);
}
```

### Protected Properties

These properties **cannot** be changed by variants:

- `position: fixed` on primary nav
- `position: fixed` on variant toolbar
- `z-index: 100` on both nav systems
- Bottom toolbar width (must remain 100%)
- Bottom toolbar position (must remain bottom)
- Accessibility attributes
- Responsive breakpoints
- Canonical data integrity

# Anti-Patterns

## Don't

- Change factual data
- Remove canonical links
- Break responsive behavior
- Use `!important` to fight specificity
- Make variants that are indistinguishable from each other
- Treat variants as color themes
- Move the variant toolbar from bottom position
- Shrink primary navigation
- Overlap variant controls with primary navigation

## Do

- Use CSS custom properties for all visual changes
- Use attribute selectors for structural overrides
- Document the design thesis for each variant
- Test all variants at all breakpoints
- Preserve canonical data integrity
- Share as much as possible across variants
- Make each variant a complete hypothesis, not a skin
- Borrow proven treatments from other variants
- Evaluate variants against real audiences

# Navigation Architecture

## Ownership Model

The portfolio has **two distinct navigation systems** that must not compete for the same visual territory:

| System | Purpose | Priority | Ownership |
|--------|---------|----------|-----------|
| Primary Navigation | Site navigation (About, Experience, Expertise, Services, Contact) | Primary | Top navigation bar |
| Variant Explorer | Experimental positioning switching | Secondary | Bottom toolbar |

### Core Principle

**Primary navigation is sacred.** It must remain permanently accessible, unobstructed, and at its default size. Variant exploration is a secondary control that must never compromise primary navigation usability.

## Layout Contract

### Primary Navigation (Top Bar)

```
Position: Fixed, top of viewport
Width: Full width
Z-index: 100
Contents: Brand/name (left), nav links (right)
Behavior: Gains background on scroll, hides when compact header appears
```

**Protected properties:**
- Top position is non-negotiable
- Right-aligned links must remain at default size
- Mobile hamburger must remain functional
- Active state highlighting must work

### Variant Explorer Toolbar (Bottom Bar)

```
Position: Fixed, bottom of viewport
Width: Full width
Z-index: 100
Contents: "Explore" label + variant buttons
Behavior: Always visible, wraps on narrow viewports
```

**Protected properties:**
- Bottom position is non-negotiable
- Full-width layout is non-negotiable
- Must not overlap primary navigation (different viewport edge)
- Body must have bottom padding equal to toolbar height

## Why Bottom Toolbar?

### Rejected Patterns

| Pattern | Reason Rejected |
|---------|-----------------|
| Top-right floating panel | Competes with primary nav for same territory |
| Dropdown from nav item | Hides variants behind interaction; reduces discoverability |
| Side drawer | Adds friction; variants should be immediately accessible |
| Top toolbar | Creates second top bar; visually noisy |

### Accepted Pattern: Bottom Toolbar

| Advantage | Explanation |
|-----------|-------------|
| Clear ownership | Top = navigation, bottom = exploration |
| No z-index conflict | Both systems use z-index: 100 on opposite edges |
| Always accessible | No hidden state, no click-to-reveal |
| Visually secondary | Bottom placement signals "supplementary" |
| Responsive-friendly | Wraps naturally on narrow viewports |
| Content-safe | Bottom bar is expected UI pattern (like chat widgets, FABs) |

## Variant Styling the Toolbar

The toolbar's **layout contract** is fixed:
- Position: fixed, bottom
- Width: full viewport width
- Z-index: 100

But its **visual expression** is variant-dependent:

```css
/* Default */
.variant-toolbar {
  background: var(--bg);
  border-top: 1px solid var(--border);
}

/* Revenue — dark mode */
[data-variant="revenue"] .variant-toolbar {
  background: #0a0a0a;
  border-top-color: #333;
}

/* Bridge — tech aesthetic */
[data-variant="bridge"] .variant-toolbar {
  background: #f8fafc;
  border-top-color: #cbd5e1;
}

/* Healthcare — clinical */
[data-variant="healthcare"] .variant-toolbar {
  background: #ffffff;
  border-top-color: #d1d5db;
}
```

**What variants MAY change:**
- Toolbar background color
- Border color/style
- Label color
- Button hover/active colors
- Button border colors

**What variants MAY NOT change:**
- Toolbar position (must remain fixed-bottom)
- Toolbar width (must remain full-width)
- Z-index (must remain 100)
- Basic layout (flex row, centered)
- Accessibility attributes (role, aria-label)


- Toolbar: May wrap to 2 rows
- Buttons: Slightly smaller
- Label: Visible

### Mobile (<768px)

```
┌─────────────────────┐
│  [☰]                │ ← Hamburger menu
│                     │
│     HERO CONTENT    │
│                     │
├─────────────────────┤
│ Exp [D][S][R][B]... │ ← Horizontal scroll or compact wrap
└─────────────────────┘
```

- Toolbar: Horizontal scroll or 2-row wrap
- Buttons: Minimal size, high touch target
- Label: May abbreviate to "Explore" or hide on very small screens

## Accessibility Rules

1. **Toolbar semantics:** `role="toolbar"` with `aria-label`
2. **Button semantics:** Each button has `aria-pressed` state
3. **Keyboard navigation:** Buttons are focusable and activatable via keyboard
4. **Screen reader:** Label announces purpose; active state is announced
5. **Focus management:** Focus outline must remain visible on all buttons
6. **Touch targets:** Minimum 44×44px effective target area

## Implementation Rules

1. **No z-index warfare:** Both nav systems use z-index: 100 on opposite edges
2. **No overlap:** Toolbar is bottom-edge only; nav is top-edge only
3. **No content occlusion:** Body has padding-bottom equal to toolbar height
4. **No arbitrary positioning:** Toolbar position is defined in CSS, not calculated by JS
5. **No variant layout escapes:** Variants cannot move the toolbar; they can only style it
6. **No duplication:** Single toolbar element, single set of buttons
7. **No inline styles:** All toolbar styling via CSS classes and variant attribute selectors

## Testing Checklist

At each breakpoint, verify:

- [ ] Primary navigation is fully visible and clickable
- [ ] Primary navigation links are at default size (not shrunk)
- [ ] Variant toolbar is fully visible
- [ ] No overlap between primary nav and variant toolbar
- [ ] No horizontal scroll on page body
- [ ] No content hidden behind toolbar
- [ ] All variant buttons are clickable
- [ ] Active variant is clearly indicated
- [ ] Mobile hamburger menu works
- [ ] Touch targets are adequate on mobile
- [ ] Focus indicators are visible
- [ ] Screen reader announces toolbar purpose

# Structural Variant Architecture

## Overview

Each variant is not merely a different color scheme. Each variant represents a **complete information architecture** — a different way of organizing, presenting, and prioritizing the same canonical content.

## Implementation Approach

The variant system uses a two-layer architecture:

### Layer 1: CSS Custom Properties (Visual Identity)
```css
[data-variant="revenue"] {
  --bg: #0a0a0a;
  --accent: #f59e0b;
  --font-display: 'Inter', sans-serif;
}
```

### Layer 2: Structural Overrides (Information Architecture)
```css
[data-variant="strategist"] [data-section="metrics"] {
  display: none;
}
[data-variant="revenue"] .hero {
  text-align: center;
  background: #0a0a0a;
}
```

### Layer 3: JavaScript DOM Restructuring (Dynamic Reordering)
```javascript
function restructureForVariant(variant) {
  // Show/hide sections based on variant
  // Reorder sections via CSS order property
  // Apply variant-specific content transformations
}
```

### JavaScript Restructuring

The `restructureForVariant()` function dynamically shows/hides sections:

```javascript
function restructureForVariant(variant) {
  // Reset all sections
  // Apply variant-specific visibility rules
  // Apply variant-specific ordering
}
```

This runs after every variant switch, ensuring the DOM reflects the selected variant's architecture.

### CSS Order Property

Sections can be reordered without changing DOM order:

```css
[data-variant="global"] [data-section="languages"] {
  order: -1; /* Move languages to top */
}
```

### Variant Contract

Each variant must preserve:
- All canonical facts (dates, companies, metrics, contact info)
- All accessibility attributes
- Responsive behavior at all breakpoints
- Primary navigation integrity
- Variant toolbar functionality

Each variant may change:
- Which sections are visible
- The visual layout of any section
- Typography, spacing, and density
- Color and background
- The order of sections via CSS `order`
- The alignment and grid structure

# Variant Design Process

## 1. Define Positioning

Before writing any CSS, answer:
- Who is this variant for?
- What opportunity does it target?
- What is Beverly's primary value prop for this audience?
- What should she be remembered for?
- What is the Design Thesis?

## 2. Choose Visual Metaphors

Match the aesthetic to the positioning:
- **Executive/Consulting:** Serif fonts, warm neutrals, generous whitespace
- **Tech/SaaS:** Sans-serif, cool tones, monospace accents
- **Clinical/Scientific:** Green palette, restrained, clean
- **Editorial/Magazine:** Italic headlines, sophisticated typography
- **Venture/Opportunity:** Warm, conversational, personal

## 3. Define Structural Changes

Beyond colors and fonts, determine:
- Hero alignment (centered vs. left)
- Section order changes
- Which sections to emphasize/hide
- Layout model (cards, timeline, grid, list)
- Density and whitespace strategy

## 4. Define CSS Variable Set

```css
[data-variant="new-variant"] {
  --bg: ...;
  --bg-alt: ...;
  --text: ...;
  --text-secondary: ...;
  --accent: ...;
  --accent-strong: ...;
  --accent-light: ...;
  --border: ...;
  --font-display: ...;
  --font-body: ...;
}
```

## 5. Override Structure and Style

Priority order:
1. Hero composition and alignment
2. Section order and visibility
3. Typography voice
4. Layout model (grid, cards, timeline)
5. Metrics presentation
6. Experience presentation
7. Services presentation
8. Outcome block
9. CTA styling

## 6. Test Responsive Behavior

- Desktop (>1024px)
- Tablet (768px-1024px)
- Mobile (<768px)

## 7. Validate Canonical Data

- All links work
- All contact info present
- All metrics unchanged
- All experience entries intact
- Design thesis is reflected in the implementation
